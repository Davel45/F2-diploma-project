# РОЗДІЛ 1. АНАЛІТИЧНИЙ ОГЛЯД ПРЕДМЕТНОЇ ОБЛАСТІ ТА ТЕХНІЧНЕ ЗАВДАННЯ

## 1.2. Інженерний конкурентний аналіз існуючих аналогів

Для обґрунтування інженерних рішень та архітектурного вибору в межах кваліфікаційного проєкту проведено системний порівняльний аналіз трьох репрезентативних програмних продуктів у доменній області диспетчеризації записів та телемедицини:
* **Doctolib** — прямий аналог, провідна європейська платформа онлайн-запису та телемедичних консультацій;
* **Cal.com** — опосередкований аналог, сучасна відкрита (open-source) платформа планування та диспетчеризації часових слотів;
* **OpenMRS** — опосередкований аналог, відкрита медична інформаційна система (EMR) з модульною підсистемою планування прийомів (Appointment Scheduling).

Аналіз виконано виключно з позицій системної архітектури, протоколів обміну, стеків сховищ даних та індустріальних обмежень (Technical Bottlenecks) на основі відкритих джерел технічної документації.

---

### 1.2.1. Системний опис продуктів-аналогів

#### 1. Doctolib
* **Архітектурний патерн та масштабованість:** Базовою архітектурою платформи виступає масштабований моноліт на базі Ruby on Rails (понад 3 млн рядків коду, підтримку якого здійснює більше 400 інженерів). Для контролю меж доменів та зв'язності кодова база модуляризована за допомогою інструменту Packwerk у незалежні модулі (engines). Організація єдиного моноліту спрощує підтримку транзакційної узгодженості даних, однак суттєво ускладнює незалежне горизонтальне масштабування окремих компонентів та оновлення версій фреймворку.
* **Протоколи передачі даних та міжсервісної взаємодії:** Клієнтська частина реалізована як React SPA, безпосередньо інтегрована в Rails-бекенд. Допоміжні та нові компоненти платформи розробляються на Java/Kotlin, TypeScript та Python у межах поступового переходу до розподілених сервісів. Специфікація міжсервісних протоколів у публічній технічній документації не розкрита.
* **Стек даних та консистентність:** Основним сховищем виступає реляційна СУБД PostgreSQL під керуванням керованого сервісу AWS Aurora (понад 10 writer-інстансів, більше 15 reader-інстансів, приблизно 10 баз даних) із сукупним обсягом понад 30 TB та піковим навантаженням близько 30 млн запитів за хвилину. Додатково застосовуються MongoDB та Redis для кешування сесій. Транзакційна консистентність спирається на механізми ACID у PostgreSQL. Механізми апаратного запобігання колізіям запису на рівні рушія СУБД у публічних джерелах компанії не деталізовані.
* **Індустріальні обмеження (Technical Bottlenecks):** Критичним інженерним викликом є необхідність постійного шардування та декомпозиції центрального сховища PostgreSQL під високим навантаженням, суттєва тривалість виконання тестових наборів у CI-контурі (понад 84 000 тестів), а також висока трудомісткість міграції базового фреймворку Rails.

#### 2. Cal.com
* **Архітектурний патерн та масштабованість:** Система реалізована за концепцією модульного монорепозиторію (Turborepo) на базі екосистеми TypeScript. Архітектура містить фронтенд-застосунок на Next.js, шар типобезпечної комунікації tRPC, виділений сервіс REST API v2 на NestJS, а також ізольовані бібліотеки пакетів і розширень інтеграцій. Подібна структура забезпечує високу швидкість кодогенерації, проте має високу зв'язаність компонентів на рівні TypeScript-типів.
* **Протоколи передачі даних та міжсервісної взаємодії:** Внутрішня комунікація між веб-клієнтом та бекендом базується на RPC-протоколі tRPC (end-to-end typesafe API). Для зовнішніх споживачів надається публічний REST API v2 з документацією OpenAPI, реалізовано механізм Webhooks для асинхронного оповіщення про події та нативні конектори до зовнішніх календарних провайдерів (Google Calendar, Microsoft Outlook API).
* **Стек даних та консистентність:** Доступ до даних організовано через PostgreSQL за допомогою Prisma ORM (схема охоплює понад 100 сутностей) із валідацією моделей бібліотекою Zod. Для збереження стану сесій та розподілених локів (Distributed Lock) у конфігурації самостійного розгортання застосовується Redis. При цьому в публічній документації відсутні відомості про використання діапазонних обмежень або предикатних блокувань ядра СУБД для запобігання овербукінгу слотів.
* **Індустріальні обмеження (Technical Bottlenecks):** Жорстка синхронна залежність від сторонніх хмарних календарних API генерує додаткову затримку (Latency) та ризики лімітування кількості запитів (Rate Limiting). Використання Prisma ORM на складній реляційній схемі спричиняє оверхед при складних аналітичних запитах, а контроль перетину часових інтервалів покладено виключно на програмний код застосунку.

#### 3. OpenMRS
* **Архітектурний патерн та масштабованість:** Побудовано за класичною модульною шаровою архітектурою (Layered Modular Architecture). Базове ядро системи (OpenMRS Core API) розширюється за допомогою плагінів у форматі OMOD, кожен з яких містить власні шари представлення, сервісної бізнес-логіки та доступу до даних. Функціонал бронювання візитів делеговано окремому модулю Bahmni Appointment Scheduling.
* **Протоколи передачі даних та міжсервісної взаємодії:** Сучасна взаємодія підтримується через REST API та галузевий медичний стандарт HL7 FHIR API. Водночас у структурі платформи залишаються застарілі механізми Direct Web Remoting (DWR) та JSP-сторінки, що створює значний технологічний борг.
* **Стек даних та консистентність:** Основним сховищем виступає реляційна СУБД MySQL, доступ до якої здійснюється через Hibernate ORM із керуванням міграціями через Liquibase. Транзакційні межі контролюються на рівні сервісів за допомогою Spring Framework. Спеціалізовані діапазонні типи даних та нативні обмеження виключення для розкладу в структурі БД не використовуються.
* **Індустріальні обмеження (Technical Bottlenecks):** Наявність застарілих технологічних компонентів (DWR, JSP, AngularJS) обмежує модернізацію UI/UX та створює ризики безпеки. Усі модулі виконуються всередині єдиного екземпляра JVM-процесу бекенда, що виключає їхнє незалежне масштабування. Структура бази даних оптимізована під збереження електронних медичних карток (EMR), а не під обробку високонавантажених конкурентних транзакцій бронювання.

### 1.2.2. Порівняльна інженерна матриця

| Критерій порівняння | Власний проєкт | Doctolib (прямий аналог) | Cal.com (опосередкований аналог) | OpenMRS (опосередкований аналог) |
| :--- | :--- | :--- | :--- | :--- |
| **Тип архітектури** | Modular Monolith, DDD, Clean Architecture | Ruby on Rails моноліт (Packwerk engines), поступова декомпозиція | Turborepo-монорепозиторій: Next.js + NestJS API v2 | Шарова модульна архітектура (Core + OMOD) |
| **Протоколи обміну (API)** | REST (Spring MVC), JWT, AMQP (RabbitMQ) | React SPA + Rails backend; міжсервісні протоколи не розкрито | tRPC, REST/OpenAPI, Webhooks | REST API, HL7 FHIR (успадковані: DWR, JSP) |
| **СУБД та сховища даних** | PostgreSQL 16+ (Flyway, Spring Data JPA), Redis 7 | PostgreSQL (AWS Aurora), MongoDB, Redis | PostgreSQL (Prisma ORM), Redis | MySQL (Hibernate ORM, Liquibase) |
| **Контроль конкурентного бронювання** | Redisson Distributed Lock + EXCLUSION CONSTRAINT (tstzrange, btree_gist) | Не розкрито у відкритих джерелах компанії | Логіка застосунку; діапазонні обмеження СУБД не описано | Транзакції Spring на рівні сервісного шару (Service Layer) |
| **Масштабування та відмовостійкість** | Virtual Threads (Java 21), RabbitMQ Waitlist Engine, Transactional Outbox | AWS Aurora: 10+ writers, 15+ readers, ~10 БД; ~30M запитів/хв | Залежність від єдиної PostgreSQL та зовнішніх calendar API | Модулі виконуються в межах єдиного JVM-процесу |
| **Technical Bottlenecks** | Обмежене незалежне масштабування модулів (trade-off Modular Monolith) | Обсяг кодової бази моноліту; необхідність декомпозиції основної БД | Мережева Latency calendar API; ORM-абстракція над великою схемою | Успадкований стек JSP/DWR; орієнтація на EMR-модель, а не на RPS |

### 1.2.3. Аналітичний інженерний висновок

Проведений системний аналіз демонструє три концептуальні підходи до побудови платформ диспетчеризації часових слотів: Doctolib використовує великомасштабний моноліт на Ruby on Rails із поступовою декомпозицією реляційного кластера PostgreSQL, Cal.com спирається на монорепозиторій екосистеми TypeScript із застосуванням Prisma ORM та tRPC, а OpenMRS реалізує шарову модульну структуру на базі стеку Spring/Hibernate з істотною часткою успадкованих рішень. Спільною характеристикою проаналізованих аналогів є відсутність у публічній технічній документації надійних гарантій часової цілісності на рівні ядра СУБД: захист від овербукінгу покладається виключно на програмну транзакційну логіку бекенда або ORM-шару, що в умовах пікового конкурентного навантаження створює ризики стану гонитви (Race Conditions) та вимагає надлишкової серіалізації транзакцій. Крім того, ключовими інфраструктурними обмеженнями конкурентних рішень залишаються високий оверхед успадкованого коду, ускладнена кодова база та залежність від зовнішніх синхронних API.

Архітектурні рішення власного кваліфікаційного проєкту безпосередньо усувають виявлені недоліки аналогів за рахунок багаторівневого захисту консистентності та сучасного реактивного стеку. Застосування патерну Modular Monolith на базі DDD та Clean Architecture забезпечує сувору ізоляцію доменних контекстів без операційної складності розподілених мікросервісних інфраструктур. На рівні збереження даних інтегровано дворівневий механізм захисту: нативний тип PostgreSQL `tstzrange` у поєднанні з розширенням `btree_gist` та обмеженням `EXCLUSION CONSTRAINT` гарантує математичну неможливість колізії часових інтервалів безпосередньо ядром СУБД, тоді як шар розподілених блокувань Redisson Distributed Lock у Redis відсікає надлишкові конкурентні запити ще до звернення до дискової підсистеми. Використання асинхронного брокера повідомлень RabbitMQ із патерном Transactional Outbox забезпечує відмовостійку диспетчеризацію черг очікування (Waitlist Engine) без виснаження пулу з'єднань СУБД, а криптографічний шар AES-256-GCM гарантує надійний захист персональних даних пацієнтів.

Обрана конфігурація становить усвідомлений інженерний компроміс (trade-off): у системі запозичено принципи модульності з явними межами доменів (аналогічно до підходу Packwerk у Doctolib та OMOD у OpenMRS) та реляційну надійність PostgreSQL, проте усунено залежність від перевірок інтервалів виключно в коді застосунку та ліквідовано технічний борг успадкованих бібліотек. Прийнятим архітектурним обмеженням є неможливість ізольованого горизонтального масштабування окремого бізнес-модуля окремо від моноліту, що повністю компенсується високою швидкістю виконання потоків Java 21 (Virtual Threads), простотою моніторингу та суворою локальною консистентністю даних. Сформовані аналітичні вимоги слугують безпосередньою основою для переходу до Розділу 2, де буде представлено детальне архітектурне проєктування за методологією C4 Model та специфікацію взаємодії компонентів.
