# Специфікація вимог до програмного забезпечення (SRS)
**Стандарт оформлення:** ISO/IEC/IEEE 29148:2018 (Systems and software engineering — Life cycle processes — Requirements engineering)  
**Проєкт:** Відмовостійка платформа телемедицини та диспетчеризації записів із механізмом апаратного запобігання овербукінгу  
**Спеціальність:** 121 / F2 «Інженерія програмного забезпечення»  
**Статус документа:** Approved (Верифіковано після технічного аудиту)  
**Версія:** 1.2 (2026-11-16)

## 1. System Context (Контекст та межі системи)

### 1.1. Призначення та межі системи (System Scope)
Програмна система являє собою централізовану відмовостійку платформу диспетчеризації амбулаторних медичних записів, ведення захищених електронних медичних карт (EMR) та супроводу телемедичних консультацій, побудовану за архітектурним патерном **Modular Monolith** на базі принципів **Domain-Driven Design (DDD)** та **Clean Architecture**.

Межі системи (System Boundary) охоплюють:
* високонавантажений контур конкурентного бронювання часових слотів прийому з дворівневою гарантією атомарності (in-memory розподілені блокування **Redis 7 / Redisson** та апаратні індекси виключення **PostgreSQL 16+ `EXCLUSION CONSTRAINT`** на типі `tstzrange`);
* подієво-орієнтований рушій електронної черги очікування (**Waitlist Engine**) на базі брокера повідомлень **RabbitMQ** та патерну **Transactional Outbox**;
* підсистему криптографічного захисту медичних даних на рівні полів (**AES-256-GCM**) та генерації цифрових рецептів із контролем цілісності (**SHA-256**);
* клієнтський односторінковий веб-застосунок (**Vue 3 SPA**) та захищений шлюз прикладного програмування (**REST API / HTTPS**).

Поза межами системи (Out of Scope) перебувають білінгові платіжні шлюзи банків-еквайрів, апаратні медичні IoT-сенсори стаціонарного моніторингу та зовнішні державні реєстри центральної компоненти eHealth, взаємодія з якими при потребі здійснюється через стандартизовані REST/FHIR-адаптери.

### 1.2. Класи користувачів (User Classes / Actors)
1. **Пацієнт (`Patient`):** зовнішній автентифікований користувач, який здійснює багатопараметричний пошук лікарів, ініціює тимчасовий холд і підтвердження бронювання слотів, реєструється в електронній черзі очікування та переглядає власні розшифровані медичні виписки й PDF-рецепти.
2. **Лікар (`Practitioner / Doctor`):** верифікований медичний фахівець, який формує індивідуальну сітку розкладу прийому, проводить очні або телемедичні консультації, вносить зашифровані клінічні протоколи в EMR та генерує електронні рецепти.
3. **Диспетчер / Адміністратор клініки (`Clinic Dispatcher / Admin`):** операційний співробітник медичного закладу, який керує довідниками спеціалізацій, опрацьовує форс-мажорні перенесення графіків, моніторить стан черги очікування та аналізує метрики утилізації робочого часу.
4. **Системний адміністратор / Офіцер безпеки (`System / Security Admin`):** інженер супроводу, який контролює стан контейнерної інфраструктури, метрики телеметрії Prometheus/Grafana, чергу недоставлених повідомлень (DLQ) та незмінний журнал аудиту доступу до медичних карток.

### 1.3. Зовнішні інтерфейси та системи (External Interfaces)
* **SMTP Email Gateway:** зовнішній поштовий сервер (протокол `SMTPS / TLS 1.3`, порт `587`) для асинхронної доставки листів-підтверджень, PDF-рецептів та нагадувань.
* **Telegram Bot API:** зовнішній хмарний шлюз месенджера (протокол `HTTPS / REST JSON`, порт `443`) для миттєвої доставки сповіщень про вивільнення слотів у черзі очікування та нагадувань про візит.
* **Time Synchronization Service (NTP):** інфраструктурне джерело точного часу для синхронізації системних годинників вузлів контейнеризації, криптографічних таймстемпів JWT та TTL розподілених блокувань Redis.

## 2. Functional Requirements (Функціональні вимоги)

Усі функціональні вимоги декомпозовані до атомарного рівня (одна вимога описує рівно одну детерміновану системну дію) відповідно до правил ISO/IEC/IEEE 29148.

### 2.1. Модуль управління розкладом та каталогом лікарів (`Scheduling & Catalog Module`)
* <a id="srs-fun-01"></a>**`SRS-FUN-01` (Генерація сітки часових слотів):** Система **повинна** генерувати та зберігати дискретні часові слоти прийому лікаря (`TimeSlot`) на основі заданого тижневого шаблону, тривалості квантування (15, 30 або 60 хвилин) і технічних перерв, представляючи кожен інтервал у реляційній СУБД типом даних `tstzrange` з явною часовою зоною UTC.
* <a id="srs-fun-02"></a>**`SRS-FUN-02` (Багатопараметричний пошук та фільтрація):** Система **повинна** виконувати фільтрацію каталогу лікарів та повертати список доступних часових слотів (`status = AVAILABLE`) за критеріями медичної спеціалізації, ідентифікатора клініки, рейтингу та заданого діапазону дат із використанням складених B-Tree та GiST індексів.

### 2.2. Модуль атомарного бронювання та захисту від овербукінгу (`Booking & Concurrency Module`)
* <a id="srs-fun-03"></a>**`SRS-FUN-03` (Тимчасовий атомарний холд слота):** При виборі вільного слота пацієнтом система **повинна** встановлювати атомарне розподілене блокування у сховищі Redis 7 (`Redisson RLock`) за ключем `slot:lock:{slotId}` із фіксованим часом життя `TTL = 600 секунд` (10 хвилин) та переводити слот у проміжний стан `RESERVED`, блокуючи паралельні спроби резервування цього слота іншими сесіями.
* <a id="srs-fun-04"></a>**`SRS-FUN-04` (Транзакційна фіксація та апаратне запобігання овербукінгу):** Під час фінального підтвердження запису система **повинна** зберігати агрегат `Appointment` у таблиці PostgreSQL 16+, де на рівні ядра СУБД діє обмеження `EXCLUSION CONSTRAINT` (`USING gist (doctor_id WITH =, slot_range WITH &&) WHERE (status IN ('RESERVED', 'BOOKED'))`), та у разі виникнення колізії перетину інтервалів гарантовано переривати транзакцію з поверненням клієнту коду `HTTP 409 Conflict`.

### 2.3. Модуль динамічної черги очікування (`Waitlist & Dispatching Module`)
* <a id="srs-fun-05"></a>**`SRS-FUN-05` (Реєстрація у черзі очікування):** Якщо у вибраного лікаря відсутні вільні слоти у заданому часовому вікні, система **має** надавати пацієнту можливість створити запис у пріоритетній черзі очікування (`WaitlistEntry`) із фіксацією часової мітки постановки у чергу (`created_at`).
* <a id="srs-fun-06"></a>**`SRS-FUN-06` (Гарантована диспетчеризація вивільненого слота за патерном Outbox):** При скасуванні підтвердженого запису (`status -> CANCELLED`) система **повинна** у межах тієї самої локальної транзакції бази даних записати подію `SlotReleasedEvent` у таблицю `outbox_events`, яку фоновий релей-процес асинхронно публікує у брокер RabbitMQ для автоматичного переведення слота в резерв за першим активним записом `WaitlistEntry`.

### 2.4. Модуль електронної медичної карти та рецептів (`EMR & Prescription Module`)
* <a id="srs-fun-07"></a>**`SRS-FUN-07` (Польове шифрування медичних записів):** Перед збереженням або оновленням сутності `EMRRecord` система **повинна** виконувати прозоре симетричне шифрування полів анамнезу, клінічного діагнозу (МКХ-10/11) та плану лікування за алгоритмом `AES-256-GCM` із генерацією унікального 96-бітного вектора ініціалізації (IV) та 128-бітного тегу автентифікації (Authentication Tag).
* <a id="srs-fun-08"></a>**`SRS-FUN-08` (Генерація та криптографічна верифікація PDF-рецептів):** За запитом лікаря система **має** формувати електронний рецепт (`Prescription`) у форматі PDF, обчислювати криптографічний дайджест `SHA-256` від канонічного набору реквізитів рецепта (ID пацієнта, ID лікаря, препарати, дозування, таймстемп) та зберігати цей хеш у базі даних для перевірки незмінності документа.

### 2.5. Модуль безпеки, автентифікації та аудиту (`Security, IAM & Audit Module`)
* <a id="srs-fun-09"></a>**`SRS-FUN-09` (Stateless автентифікація та RBAC-авторизація):** Система **повинна** здійснювати автентифікацію користувачів з видачею пари токенів `JWT` (`Access Token` із часом дії 15 хвилин та `Refresh Token` із часом дії 7 діб) та примусово перевіряти рольові повноваження (`ROLE_PATIENT`, `ROLE_DOCTOR`, `ROLE_CLINIC_ADMIN`, `ROLE_SYS_ADMIN`) на кожному захищеному REST-ендпоінті.
* <a id="srs-fun-10"></a>**`SRS-FUN-10` (Незмінне логування доступу до медичних даних):** Система **повинна** автоматично реєструвати подію безпеки `AuditEvent` (ID суб'єкта, роль, IP-адреса, тип операції `READ/WRITE`, ID запису `EMRRecord`, таймстемп UTC) у спеціалізованій append-only таблиці аудиту при кожному зверненні до зашифрованих медичних карток.

### 2.6. Модуль асинхронних сповіщень та аналітики (`Notification & Analytics Module`)
* <a id="srs-fun-11"></a>**`SRS-FUN-11` (Ізольована доставка сповіщень із Retry та DLQ):** Система **повинна** відправляти зовнішні сповіщення (підтвердження запису, сповіщення черги очікування, планові нагадування за 24 год і 2 год) виключно через асинхронні черги RabbitMQ, застосовуючи при збоях зовнішніх шлюзів політику `Exponential Backoff Retry` (3 спроби з інтервалами 5 с, 30 с, 120 с) та маршрутизуючи недоставлені повідомлення у `Dead Letter Queue (DLQ)` без відкату основної бізнес-транзакції.
* <a id="srs-fun-12"></a>**`SRS-FUN-12` (Агрегація операційної аналітики клініки):** Система **має** обчислювати та надавати адміністратору клініки агреговані статистичні метрики за вибраний часовий інтервал: коефіцієнт завантаженості слотів лікаря (`Utilization Rate, %`), частку скасованих візитів та відсоток неявок пацієнтів (`No-Show Rate, %`).

## 4. Verification Criteria (Критерії та методи інженерної верифікації)

Кожна вимога контракту SRS має однозначний інструментальний метод перевірки, що виконується в автоматизованому пайплайні CI/CD (GitHub Actions) або під час стендового навантажувального аудиту:

1. **Верифікація атомарності та відсутності овербукінгу (`SRS-FUN-03`, `SRS-FUN-04`, `SRS-NFR-REL-01`):**
   * *Метод:* Інтеграційний багатопотоковий стрес-тест на базі **JUnit 5**, `CountDownLatch` / `CyclicBarrier` (100 конкурентних віртуальних потоків Java 21 одночасно викликають ендпоінт бронювання одного слота) у середовищі **Testcontainers** (реальні контейнери PostgreSQL 16 та Redis 7).
   * *Критерій успішності:* Рівно 1 потік отримує статус `HTTP 201 Created`, решта 99 потоків отримують `HTTP 409 Conflict`; у таблиці `appointments` присутній рівно 1 запис.
2. **Верифікація продуктивності та часу відгуку (`SRS-NFR-PERF-01`, `SRS-NFR-PERF-02`, `SRS-NFR-PERF-03`):**
   * *Метод:* Автоматизоване навантажувальне тестування утилітою **Grafana k6** за сценаріями *Steady-State Load* (500 RPS протягом 10 хвилин) та *Spike Testing* (стрибок до 1000 RPS за 30 секунд) зі збором метрик через **Spring Boot Actuator**, **Micrometer** та **Prometheus**.
   * *Критерій успішності:* Перцентиль `http_req_duration{p(95)} < 150 ms` для GET-запитів розкладу, `< 250 ms` для POST-запитів бронювання, рівень помилок `http_req_failed < 0.1%`.
3. **Верифікація відмовостійкості черг та Outbox (`SRS-FUN-05`, `SRS-FUN-06`, `SRS-FUN-11`, `SRS-NFR-REL-03`):**
   * *Метод:* Хаос-тестування (Chaos Engineering) за допомогою **Testcontainers Toxiproxy** (примусове блокування TCP-з'єднання до SMTP/Telegram шлюзу та симуляція мережевої затримки 5000 мс під час скасування запису).
   * *Критерій успішності:* Основна транзакція скасування завершується за `< 200 мс`; подія фіксується в `outbox_events`; після 3 невдалих спроб доставки з експоненційним бекофом повідомлення автоматично переміщується в чергу `notifications.dlq` брокера RabbitMQ без втрати корисного навантаження (payload).
4. **Верифікація криптографії, безпеки та Rate Limiting (`SRS-FUN-07`, `SRS-FUN-08`, `SRS-FUN-09`, `SRS-FUN-10`, `SRS-NFR-SEC-01`..`04`):**
   * *Метод:* Автоматизовані тести безпеки **Spring Security Test**, криптографічні юніт-тести перевірки `AES-256-GCM` (детекція підміни 1 біта шифротексту через `AEADBadTagException`) і `SHA-256`, перевірка лімітів `HTTP 429` серією з 65 запитів/хв у **Postman / Newman**, а також сканування залежностей та Docker-образів сканером **Trivy**.
   * *Критерій успішності:* 100% проходження тестів рольової ізоляції RBAC, неможливість прочитати відкритий текст діагнозу напряму через `SELECT` із таблиці БД, наявність запису в `audit_events` після кожного звернення до EMR.
5. **Верифікація якості коду та архітектурної чистоти (`SRS-NFR-MAINT-01`, `SRS-NFR-MAINT-02`):**
   * *Метод:* Статичний аналіз коду в **SonarQube** та архітектурні фітнес-функції **ArchUnit** (перевірка відсутності прямих залежностей контролерів від шару JPA-репозиторіїв та ізоляції модулів DDD).
   * *Критерій успішності:* Проходження статусу `Quality Gate: PASSED`, тестове покриття ядра `>= 80%`, `0` порушень правил ArchUnit.

## 5. Glossary (Інженерний глосарій)

* **`Exclusion Constraint` (Обмеження виключення PostgreSQL):** декларативне правило цілісності на рівні ядра реляційної СУБД, яке на базі узагальненого дерева пошуку **GiST (`btree_gist`)** гарантує, що для жодних двох рядків таблиці з однаковим `doctor_id` значення часових діапазонів `tstzrange` не перетинаються (оператор `&&`).
* **`tstzrange` (Timestamp with Time Zone Range):** нативний діапазонний тип даних PostgreSQL, що представляє неперервний інтервал часу з урахуванням часового поясу `[start_time, end_time)` та підтримує атомарні топологічні оператори перетину й входження.
* **`Distributed Lock` (Розподілене блокування Redisson):** механізм взаємного виключення (mutex) у розподіленому In-Memory сховищі **Redis**, який використовує атомарні Lua-скрипти та механізм Pub/Sub для тимчасового резервування слота (TTL 10 хвилин) без блокування з'єднань основної реляційної бази даних.
* **`Transactional Outbox` (Транзакційна вихідна скринька):** архітектурний патерн надійного обміну повідомленнями, за якого бізнес-сутність та подія для брокера черг записуються в одну реляційну базу даних у межах єдиної ACID-транзакції, що усуває проблему подвійного запису (Dual-Write Problem).
* **`Dead Letter Queue (DLQ)` (Черга недоставлених повідомлень):** спеціалізована черга в брокері **RabbitMQ**, куди через `Dead Letter Exchange (DLX)` автоматично перенаправляються повідомлення, обробка яких завершилася помилкою після вичерпання ліміту повторних спроб (`Retry`), для подальшого аудиту та перевідправки.
* **`AES-256-GCM` (Advanced Encryption Standard — Galois/Counter Mode):** симетричний блоковий алгоритм автентифікованого шифрування з приєднаними даними (AEAD) та довжиною ключа 256 біт, який одночасно забезпечує конфіденційність медичних записів (EMR) та криптографічний контроль їхньої цілісності.
* **`Virtual Threads` (Віртуальні потоки Java 21 / Project Loom):** легковагові призначені для користувача потоки виконання у JVM, які керуються віртуальною машиною поверх невеликого пулу потоків ОС (carrier threads) і дозволяють обслуговувати тисячі одночасних I/O-операцій (запити до БД, Redis, RabbitMQ) без блокування системних потоків.
* **`Latency p95 / p99` (Перцентилі затримки відгуку):** статистичні метрики продуктивності, що визначають максимальний час обробки запиту, у який вкладаються відповідно 95% або 99% усіх звернень до системи за певний інтервал спостереження.
