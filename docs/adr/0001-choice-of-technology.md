# ADR-001: Вибір механізму забезпечення атомарності бронювання та апаратного запобігання овербукінгу (Redis Redisson Lock + PostgreSQL Exclusion Constraints)

* **Статус:** `Approved (Затверджено)`
* **Дата прийняття:** 2026-11-16
* **Автори та рецензенти:** Ковальчук В. С. (System Architect), Дячук Р. Л. (Науковий керівник / Principal Reviewer)
* **Пов'язані вимоги SRS:** [`SRS-FUN-03`](../srs.md#srs-fun-03), [`SRS-FUN-04`](../srs.md#srs-fun-04), [`SRS-NFR-PERF-01`](../srs.md#srs-nfr-perf-01), [`SRS-NFR-PERF-03`](../srs.md#srs-nfr-perf-03), [`SRS-NFR-REL-01`](../srs.md#srs-nfr-rel-01)

## 1. Context (Інженерний контекст та проблема)

Під час проєктування ядра платформи телемедицини та диспетчеризації записів виникає фундаментальна проблема розподілених систем — **стан гонитви (Race Condition)** при конкурентному бронюванні обмежених часових слотів прийому лікаря. У моменти відкриття запису до профільних спеціалістів декілька десятків або сотень клієнтських потоків одночасно надсилають запит на резервування одного часового інтервалу `[start_time, end_time)`.

Інженерне рішення повинно одночасно задовольняти чотири жорсткі обмеження контракту [`srs.md`](../srs.md):
1. **Бізнес-інваріант двофазного резервування ([`SRS-FUN-03`](../srs.md#srs-fun-03)):** пацієнту після вибору слота надається рівно **10 хвилин (600 секунд)** тимчасового холду для внесення даних анамнезу та підтвердження запису. Протягом цього вікна слот має бути заблокованим для інших користувачів, але автоматично вивільнятися, якщо пацієнт покинув сторінку.
2. **Абсолютна відсутність подвійного запису ([`SRS-FUN-04`](../srs.md#srs-fun-04), [`SRS-NFR-REL-01`](../srs.md#srs-nfr-rel-01)):** система не має права допустити жодної колізії перетину часових інтервалів для одного лікаря навіть у випадку часткової деградації кешу або помилок у бізнес-логіці коду.
3. **Висока пропускна здатність ([`SRS-NFR-PERF-01`](../srs.md#srs-nfr-perf-01)):** цільове стабільне навантаження становить **500 RPS** (пікове — до **1000 RPS**) без виснаження пулу з'єднань реляційної бази даних (`HikariCP`).
4. **Низька затримка відгуку ([`SRS-NFR-PERF-03`](../srs.md#srs-nfr-perf-03)):** час обробки запиту на бронювання на 95-му перцентилі (`p95 Latency`) не повинен перевищувати **250 мс**.

## 2. Alternatives (Розглянуті архітектурні альтернативи)

### Альтернатива А: Песимістичне блокування на рівні реляційної СУБД (`SELECT ... FOR UPDATE` або рівень ізоляції `SERIALIZABLE`)
* **Суть підходу:** Використання виключно реляційної СУБД PostgreSQL із блокуванням рядка слота (`PESSIMISTIC_WRITE`) або переведенням транзакцій бронювання у рівень ізоляції `SERIALIZABLE` (SSI — Serializable Snapshot Isolation).
* **Технічні переваги:** Відсутність потреби у додатковому In-Memory сховищі; проста інтеграція зі стандартним Spring Data JPA.
* **Причини відхилення (Інженерні обмеження):**
  * **Виснаження пулу з'єднань (Connection Pool Exhaustion):** утримання відкритої SQL-транзакції з `SELECT ... FOR UPDATE` на час тимчасового холду пацієнта (до 10 хвилин) є архітектурним антипатерном — стандартний пул `HikariCP` (20–50 фізичних з'єднань) повністю блокується вже після 50 одночасних користувачів.
  * **Проблема фантомних інтервалів:** `SELECT ... FOR UPDATE` блокує лише існуючі рядки; якщо слоти формуються динамічно або зсуваються за тривалістю (наприклад, 20 хв замість 30 хв), блокування рядка не захищає від вставки нового запису, що частково перетинається за часом.
  * **Деградація Latency при `SERIALIZABLE`:** при 500 RPS конкурентні транзакції генерують масові помилки серіалізації (`SQLState 40001`), підвищуючи `p95 Latency` до `> 1200 мс`.

### Альтернатива Б: Оптимістичне блокування в ORM (`@Version`) або використання документної NoSQL СУБД (`MongoDB`)
* **Суть підходу:** Зберігання слотів і записів у документній колекції MongoDB або реляційній таблиці з числовим полем версії `@Version` у Hibernate 6, де перевірка перетину інтервалів виконується програмним запитом перед збереженням.
* **Технічні переваги:** Висока швидкість читання; відсутність довготривалих блокувань на рівні бази даних; гнучка схема документів для медичних анкет.
* **Причини відхилення (Інженерні обмеження):**
  * **Відсутність апаратних діапазонних обмежень у MongoDB:** MongoDB не підтримує нативних індексів виключення неперервних часових відрізків (аналогів GiST `&&`). Перевірка перетину часу типу `startA < endB AND endA > startB` на рівні коду вразлива до аномалії *Write Skew* між операціями читання та запису.
  * **Шторм помилок при «гарячих» слотах:** оптимістичне блокування (`@Version`) працює лише при оновленні існуючого рядка і викликає лавину винятків `ObjectOptimisticLockingFailureException` при одночасному зверненні сотень клієнтів, перекладаючи навантаження повторних спроб на мережу та CPU сервера.

### Альтернатива В (Обрана): Дворівневий гібридний механізм — розподілені блокування в Redis 7 (`Redisson Distributed Lock`) + апаратні обмеження ядра PostgreSQL 16+ (`tstzrange` та `EXCLUSION CONSTRAINT` на базі `btree_gist`)
* **Суть підходу:** Розділення відповідальності на два ешелони:
  1. **Перший ешелон (Швидкий In-Memory фільтр та тимчасовий холд):** клієнт Redisson атомарно захоплює розподілений лок у Redis 7 (`slot:lock:{doctorId}:{slotId}`) із жорстким `TTL = 600 с` (10 хвилин) за час `< 2 мс`. Усі конкурентні запити на цей слот відсікаються в оперативній пам'яті без жодного звернення до диска PostgreSQL.
  2. **Другий ешелон (Апаратний інваріант цілісності СУБД):** у таблиці `appointments` PostgreSQL 16+ інтервал візиту зберігається у нативному типі `tstzrange`, а на таблицю накладено апаратне обмеження `EXCLUSION CONSTRAINT` із індексом `btree_gist`, яке на рівні ядра СУБД блокує перетин будь-яких інтервалів (`&&`) для одного `doctor_id`.

## 3. Decision (Прийняте рішення та технічне обґрунтування)

Затверджено **Альтернативу В**: реалізацію дворівневого контуру захисту від овербукінгу у складі **Redis 7 (Redisson)** та **PostgreSQL 16+ (`tstzrange` + `EXCLUSION CONSTRAINT`)**.

### Технічна специфікація ядра рішення:
1. На рівні міграцій бази даних (**Flyway**) активується розширення `btree_gist` та створюється фізичне обмеження виключення:
   ```sql
   CREATE EXTENSION IF NOT EXISTS btree_gist;

   ALTER TABLE appointments
   ADD CONSTRAINT excl_doctor_overlapping_slots
   EXCLUDE USING gist (
       doctor_id WITH =,
       appointment_range WITH &&
   )
   WHERE (status IN ('RESERVED', 'BOOKED'));
   ```
2. Часові межі інтервалу задаються напіввідкритим діапазоном `[start_time, end_time)` (нижня межа включно, верхня виключно), що дозволяє стикувати сусідні візити (наприклад, `10:00–10:30` та `10:30–11:00`) без помилкового спрацювання колізії.
3. Шар Redis виконує роль високопродуктивного буфера (Traffic Shaper): при піковому навантаженні 1000 RPS 99% дублюючих запитів отримують швидку відмову на рівні Redisson за `< 5 мс`, зберігаючи пул з'єднань PostgreSQL вільним для легітимних транзакцій та читання EMR.
4. Навіть у випадку повного падіння або перезавантаження вузла Redis (втрата in-memory локів), другий рубіж у вигляді `EXCLUSION CONSTRAINT` у PostgreSQL математично унеможливлює появу овербукінгу, генеруючи виняток `SQLState 23P01 (exclusion_violation)`, який `GlobalExceptionHandler` трансформує у детерміновану відповідь `HTTP 409 Conflict`.

## 4. Consequences (Наслідки та архітектурні компроміси — Trade-offs)

### Позитивні наслідки (Positive Consequences)
* **Абсолютна гарантія консистентності (`Zero Overbooking`):** захист реалізовано на найнижчому можливому рівні — в індексному дереві GiST ядра реляційної СУБД, що виключає людський фактор або помилки в Java-коді.
* **Виконання жорстких SLA за затримкою (`p95 < 250 мс`):** розвантаження PostgreSQL за рахунок відсікання конкурентних колізій у Redis дозволяє стабільно тримати 500–1000 RPS на одному інстансі бази даних.
* **Нативна підтримка 10-хвилинного холду:** механізм TTL у Redis автоматично очищує покинуті резерви без необхідності важких SQL-завдань за розкладом (`cron cleanup`).

### Негативні наслідки, приховані ризики та вартість рішення (Negative Consequences & Risks)
1. **Зростання інфраструктурної та FinOps-складності:** система вимагає розгортання, моніторингу та резервування двох гетерогенних сховищ даних (`PostgreSQL 16` + `Redis 7`), що збільшує споживання оперативної пам'яті контейнерного середовища приблизно на `256–512 MB RAM` та ускладнює конфігурацію `docker-compose.yml`.
2. **Ускладнення ORM-шару та сповільнення CI/CD пайплайну:**
   * Стандартна специфікація Jakarta Persistence (JPA / Hibernate 6) не підтримує тип `tstzrange` із коробки — необхідне підключення додаткової бібліотеки `io.hypersistence:hypersistence-utils-hibernate-63` та написання кастомних маперів.
   * Оскільки легковагова in-memory база `H2` не підтримує розширення `btree_gist` та `EXCLUDE USING gist`, усі інтеграційні тести репозиторіїв **зобов'язані** запускатися у реальному Docker-контейнері PostgreSQL через **Testcontainers**, що збільшує час проходження пайплайну GitHub Actions на **30–45 секунд**.
3. **Технологічний Vendor Lock-in на PostgreSQL:** використання пропрієтарних для PostgreSQL механізмів `tstzrange` та `btree_gist` унеможливлює просту заміну СУБД на MySQL, MariaDB або MS SQL Server без повного перепроєктування модуля диспетчеризації.
4. **Ризик граничних станів при закінченні TTL (Lock Expiration Edge Case):** якщо клієнтський запит підтвердження бронювання надійшов на 599-й секунді холду і затримався через GC-паузу або мережевий лаг, лок у Redis може спливти до завершення SQL-транзакції. *Мітигація:* фінальним арбітром завжди виступає транзакція PostgreSQL із `EXCLUSION CONSTRAINT`, а перед записом у БД виконується атомарна перевірка валідності токена володіння локом (`fencing token`).
